# Stage A Diagnostics: Recommender Quality Audit

This document summarizes the findings from the diagnostic investigation of the Stage A Recommendation Models. The investigation was triggered by severe anomalies identified during the offline evaluation, including the Hybrid model defaulting to 100% Collaborative Filtering, contradictory cold-start metrics, and extremely low overall recommendation quality.

---

## Section 1: Metric Validation Results

A re-computation of the evaluation metrics confirmed the validity of the previous output. The metrics are indeed accurate, which unfortunately confirms that the models are performing extremely poorly:
- **Precision@10**: ~0.002
- **Recall@10**: ~0.010
- **NDCG@10**: ~0.006

These values are barely above random chance. The validation process confirms there is no error in the metric calculation logic itself; rather, the models are fundamentally failing to rank relevant items in the top-K slots.

---

## Section 2: Cold-Start Audit Findings

The contradiction between the cold-start metrics table (reporting 0.0 for all metrics) and the narrative discussion has been identified.

**Findings:**
1. **Empty Cohort**: The evaluation logic defines a cold-start user as someone with `<= 1` training interactions. However, the recently implemented **user-level chronological split** allocates exactly 70% of *each user's* interactions to the Train set. Since every synthetic user was generated with exactly 10 interactions, every user has exactly 7 interactions in the Train set. Thus, the number of cold-start users in the Test set is exactly **0**.
2. **Hardcoded Narrative**: The narrative text in the evaluation report discussing the performance of CB vs CF on cold-start users was statically hardcoded in the `evaluate_recommenders.py` script. It was printed regardless of the actual computed results.

---

## Section 3: Hybrid Failure Root Cause

The Hybrid model optimization grid search selected $\alpha = 1.0$, effectively nullifying the Content-Based (CB) component and relying 100% on Collaborative Filtering (CF).

**Findings:**
1. **Calibration Mismatch**: While `hybrid.py` attempts to apply Min-Max scaling to both CB and CF scores before blending them, the underlying score distributions are vastly different. CB scores are cosine similarities densely clustered near 0.8-0.9, while CF scores are predicted ratings spread between 1.0 and 5.0.
2. **Strict Superiority in Grid Search**: Because the CF model yielded a marginally higher NDCG on the validation set than the CB model (0.0097 vs ~0.0050), the grid search optimization naturally pushed the blending weight entirely to the CF model to maximize the validation metric. Blending in the weaker CB model only dragged the metric down.

---

## Section 4: Collaborative Filtering Root Cause

The Collaborative Filtering SVD model yielded an NDCG@10 of 0.0097, which is incredibly low.

**Findings:**
1. **Extreme Sparsity**: The user-item matrix consists of 500 users and 1,379 hotels, yielding ~689,500 possible pairs. With only 5,000 total interactions, the matrix sparsity is **99.27%**. 
2. **Insufficient Item Support**: 5,000 interactions distributed across 1,379 hotels means the average hotel only has ~3.6 interactions. SVD matrix factorization cannot learn meaningful latent item factors with such scarce support. The model heavily underfits, reverting to predicting the global mean plus item biases.

---

## Section 5: Content-Based Root Cause

The Content-Based model performed worse than the Popularity Baseline.

**Findings:**
1. **Overspecialization**: The explicit user profile strictly emphasizes exact matches for `preferred_area` and `budget_category`. If a user's ground-truth test interactions contain hotels slightly outside their stated strict budget or area, the CB model heavily penalizes them and fails to retrieve them.
2. **Implicit Profile Dilution**: The implicit user profile is generated by averaging the vectors of interacted hotels. Because the synthetic interactions are highly scattered, this average vector becomes a "gray mush" that fails to strongly align with any specific niche of hotels, destroying the cosine similarity scoring.

---

## Section 6: Interaction Dataset Quality Assessment

The root cause of *all* model failures ultimately traces back to the synthetic interaction generation logic.

**Findings:**
1. **Weak Preference Signals**: The interaction generation script (`generate_interactions.py`) appears to have assigned views, clicks, and bookings with too much randomness. 
2. **Lack of Correlation**: There is very little correlation between a user's stated demographic preferences (e.g., Budget, Area) and the hotels they interacted with. Because the ground-truth test interactions are effectively random, the personalized models (CB and CF) cannot predict them. Conversely, the Popularity Baseline performs "better" simply because predicting globally popular items is a safer bet when personalization signals are absent.

---

## Section 7: Recommended Remediation Options

To rescue the recommendation system, the following remediations must be applied:

1. **Rebuild Synthetic Interactions**: The `generate_interactions.py` script must be overhauled. Users must have a heavily weighted probability of interacting with hotels that actually match their budget, area, and amenity preferences. We also need to generate a power-law distribution of user activity (some users with 50+ interactions, some with 0-1 interactions) to properly test cold-start scenarios.
2. **Implement Rank Fusion**: Replace score-based linear blending in the Hybrid model with Reciprocal Rank Fusion (RRF). RRF combines the *rankings* from CB and CF rather than the raw scores, completely bypassing the calibration mismatch issue.
3. **Dynamic Evaluation Reporting**: Remove all hardcoded narrative conclusions from the evaluation script to prevent contradictory reporting.

---

## Section 8: Go / No-Go Decision

**Status: NO-GO**

The project is **NOT READY** to proceed to Stage B (Explainability), Stage C (RAG Pipeline), or Stage D (Streamlit Dashboard).

**Reasoning:**
Proceeding to Stage B would involve building SHAP explainers to interpret the models. Currently, the models are attempting to predict random noise due to the flawed synthetic interactions. Building an explainability layer on top of a model that has learned nothing will yield nonsensical explanations (e.g., SHAP will assign random feature importance). 

We must halt execution and apply the remediations in Section 7 (fixing data generation and hybrid fusion logic) to achieve a baseline NDCG@10 of at least ~0.05 - 0.10 before moving to the Explainability stage.
